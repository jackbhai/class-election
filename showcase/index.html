01 · What it is

An election, end to end.
Not a demo.

This is my college project: a real voting system for class Monitor and CR. Verified voters, a hidden admin console, and a fraud-checked audit trail — every vote real, every check server-side.

Verified voters only

Sign up, register for the election, pass admin review — then one vote per person. Double-voting is blocked at the database level, not just the UI.

Two races, one ballot

Each voter picks a Monitor and a CR in a single flow, then receives an XXXX-XXXX receipt proving the vote was counted.

Fraud-checked, honestly

Votes are linked to voters for audit — admins can spot duplicate phones or fake votes in a read-only audit view, but can never change a vote.

Admin console, hidden by design

The admin panel lives at a hidden route — no link, no hint anywhere in the voter UI. Elections, candidates, registrations, audit and settings live there.

02 · Why I built this

Paper chits had
to go.

My class still voted on paper chits. Someone collected them, someone counted them, and every single time there was a fight about the counting. I wanted to build the thing I would actually trust to run our Monitor election — not a demo with fake data, a real app with a real database.

I picked Supabase because I wanted to learn how real auth and real row-level security work — not localStorage tricks. Most of what I know about Postgres now, I learned the hard way: usually late at night, usually because something was on fire. The diary below has the receipts.

It's still a college project. The code is mine, the mistakes were mine, and the fixes are all in here too.

05 · How voting works

Six steps.
One honest vote.

This is the exact path a voter walks. I kept it as short as I could without skipping the checks that matter.

  1. Sign up

    Create an account with email and password. Supabase Auth handles the session — no codes to remember, nothing to lose.

  2. Register for the election

    Fill the fields the admin configured — name, class, enrollment, mobile number — and upload an ID photo if the election requires one.

  3. Get approved

    An admin reviews every registration, sees the ID thumbnail, and verifies or rejects. Only verified voters reach the ballot.

  4. Vote

    Pick one Monitor and one CR. A single atomic database call writes the vote — row locks plus a uniqueness constraint make a double vote impossible.

  5. Keep your receipt

    You get an XXXX-XXXX receipt the moment your vote lands. If the network drops mid-vote, replaying safely returns your original receipt — never a second vote.

  6. Watch results

    When voting closes, the admin publishes results and everyone sees the winners — with tallies, not black boxes.

The admin side

Admins sign in at the hidden #/admin.html route — Overview, Elections, Candidates, Registrations, Vote Audit, Settings. The Vote Audit tab is strictly read-only: who voted for whom, receipt, timestamp, duplicate-phone warnings, CSV export. Admins can inspect everything and change nothing.

09 · Security, layer by layer

I don't trust the browser.
So the app doesn't either.

Every layer below is enforced by the database, and I verified each one against the live project. The UI promises nothing the server doesn't back up.

08

Legacy path revoked

Migration v7 revoked every grant on the old token-based vote function — obsolete codes can never become votes.

07

Admins are gated, not trusted

Every admin RPC checks the caller's role server-side. The first-admin bootstrap is disabled and profiles can't self-promote.

06

Zero policies on the votes table

Nobody — not even an admin — can read, insert, update or delete votes through the API. Only the vote function writes.

05

Atomic vote RPC

Row locks plus a uniqueness constraint: one verified registration, one vote. Double-votes fail at the database.

04

Auth-bound registration

Votes require a verified registration tied to your login. No registration, no ballot.

03

RLS on every table

Anonymous callers can't read or write tables directly. The only door in is a server-side function.

02

SHA-256 hashed codes

The legacy one-time voting codes were stored as hashes — raw secrets never sat in the database.

01

Browser holds only the anon key

The service_role key never ships to the client. The browser is untrusted by design.

10 · How it was built

Files in a project.
A database doing the heavy lifting.

Seven migrations, applied one by one to the live database. The timeline below is the real order I built things in.

Browser

Vanilla JS SPA · hash routes
index.html · app.js · styles.css

Supabase

AuthPostgREST · RPCPostgres · RLSStorage · ID slots

Seven migrations, in order

  1. v1

    Foundation

    Base schema: elections, candidates, SHA-256-hashed one-time voting codes, atomic vote RPC, RLS, admin roles.

  2. v2

    Secure admin auth + hardened ID uploads

    Admin profiles, slot-bound expiring ID upload paths, ID verification records.

  3. v3

    Security patches

    RLS-safe upload slot checks; a vote counts only when the ID file actually exists in storage.

  4. v4

    Signup-based flow

    Voter registrations with admin review, candidate photos and manifestos — no codes needed.

  5. v5

    ID enforcement + vote idempotency

    Server-side ID checks on approval; a lost response replays the original receipt, never a second vote.

  6. v6

    Phone identity + vote audit

    10-digit mobile verification per voter and a read-only admin audit with duplicate-phone fraud flags.

  7. v7

    Legacy lockdown

    All grants revoked on the obsolete token-based vote function — old codes can never become votes.

11 · Build steps

Recreate this yourself.
Six steps, no magic.

Everything below is real — the same order I did it in. Tap the copy button on any command.

1

Get the source files

The whole app is plain files — no bundler, no build. Download the project folder; this is all there is:

index.html styles.css app.js config.js supabase/schema.sql supabase/migration_v2.sql … migration_v7.sql
2

Create a free Supabase project

Free tier is plenty. Then copy your Project URL and anon key from Project Settings → API.

# supabase.com → New project, then copy: PROJECT_URL=https://xyzcompany.supabase.co ANON_KEY=sb_publishable_...
3

Run the schema, then the migrations

In the Supabase SQL Editor, run the base schema first, then migrations v2 → v7 in order.

supabase/schema.sql supabase/migration_v2.sql supabase/migration_v3.sql supabase/migration_v4.sql supabase/migration_v5.sql supabase/migration_v6.sql supabase/migration_v7.sql
4

Paste the keys into config.js

The only setup file in the project — two values, and the frontend is connected.

// config.js SUPABASE_URL: "https://xyzcompany.supabase.co", SUPABASE_ANON_KEY: "sb_publishable_..."
5

Put it online

The app is just static files — drag the project folder onto any static host and it's live. No build step, no config needed.

Any static host works — it's only HTML, CSS and JS.

6

Sign up the first admin

Open the app, create your admin account, and launch your first election. Done.

# open the app → sign up → create an election → share the link

13 · Build diary

Notes I wrote
while building.

Unedited, more or less. Everything here actually happened.

  1. 21 Sep

    Every vote was failing and I had no idea why. Turns out Supabase keeps pgcrypto's gen_random_bytes in the extensions schema, not public — and my function said set search_path = public. One-line fix: set search_path = public, extensions. Felt like a genius for about ten minutes.

  2. 21 Sep

    Signup created the account but returned no session, so new users landed on a dead screen. Added a direct sign-in fallback right after signup. The contradiction was ugly; the fix was three lines.

  3. 21 Sep

    Spent an hour convinced my router was broken because #/register showed "Election not found". Those routes need ?election=<id> in the URL — the router was fine. I was not.

  4. 21 Sep

    Shipped migration v7: revoked every grant on the legacy token vote function, so old codes can never become votes. Kept the function body though — reversible, just in case.

  5. 21 Sep

    Deploy scare: one bad upload wiped README.md, supabase/ and .gitignore. Restored them from an older backup snapshot of the project tree and redeployed. I check the file list before every deploy now.

  6. 21 Sep

    Supabase login hit me with an hCaptcha: pick the animal half-hidden behind a line. Solved it like an exam question and got back to work.

15 · Bugs I actually hit

Three good ones.
All survived by the code.

bug

Every vote failed with a database error

Cause: cast_vote used set search_path = public, but Supabase installs pgcrypto's gen_random_bytes under the extensions schema.

Fix: every RPC now sets search_path = public, extensions, and cast_vote became create or replace.

bug

New users signed up, then stared at a dead screen

Cause: signup sometimes returned no session — the app expected one and rendered nothing.

Fix: a direct signIn fallback immediately after signup. Ugly contradiction, clean fix.

not a bug

#/register and #/vote said "Election not found"

Cause: those routes require an ?election=<id> hash param — opening them bare is the designed gated state.

Fix: none needed. But it cost me an hour, so it earned a card.
